## 锁达妙 yaw —— 方案对比（给用户的结论：选 C）
达妙 `[1]` 是 SPEED 模式，但**反馈帧任何模式都返回 pos/vel/torque**（`State_Decode` 无条件解析）⇒ SPEED 下 `pos` 有值。

| 方案 | 做法 | 抗扰 | 回位 | 改动 |
|---|---|---|---|---|
| A 失能 | 停 `DMmotorinit` + 发 `0xFD` | 无 | 无 | 小 |
| B 速度锁 0 | `setSpeed=0`（现状） | 抗速度不抗位置 | ❌ | 极小 |

## 补充实读（2026-10-05 下午，用户定"用 C 方案锁电机"）

### CRC 相关硬事实
- `usart.cpp:459` ISR 用 `xQueueOverwriteFromISR(handle, m_uartrx, NULL)` → **整块 100 字节入队**（`UART_MAX_LEN=100`，队列 item size 也是 100）
  ⇒ **帧长无法从队列 item 得到**；帧后面的字节是上一帧残留 ⇒ **必须定长帧 + 固定偏移读**。变长帧则必须在帧头带长度字段
  ⇒ 顺带：`dataDmaNum` 从未被写，ISR 也没读 `__HAL_DMA_GET_COUNTER` → 帧长信息在 ISR 层就丢了
- `CRC_TAB` 首项 `0x1189, 0x2312, 0x329B…` = **反射式 0x8408 表**（poly 0x1021 反射）＋ `CRC16_INIT=0xFFFF` ⇒ **CRC-16/MCRF4XX**，即 **RoboMaster 官方视觉协议那一套**。`append`/`verify` 都是**低字节在前**、初值 `0xFFFF`、覆盖 `len-2` → 两端自洽 ✓
- ⚠️ `xuc.cpp:43` `++rx_count;` 写在 `if (0xA5)` **外面** → 噪声帧、半帧都会计入 → `pc_timeout` 永不超时
- ⚠️ `RxPacket RxNuc` 是个错误假设（只有 header+checksum 两字节），零使用，建议删，留着误导

### C 方案（软位置锁）落地要点
- `DMMOTOR::State_Decode` **不校验 ID**：零缓冲时 `idata[id][0]&0x0F == 0`，与 ID 0x09/0x06 都不符 ⇒ 把 `(idata[id][0]&0x0F)==(this->ID&0x0F)` 这个判断**搬进 `State_Decode`**，在那里置 `decoded=true`，顺手解 `status = idata[id][0]>>4`。`PANTILE::Update()` 只读 `decoded`
- 输出受 `DMmotor_Ontimer` 的 `LIMIT_MIN_MAX(setSpeed, ±10 rad/s)` 自动钳制；`setSpeed` 是全局对象成员 → 上电为 0，`decoded` 不成立时保持 0，安全
- `DMmotor[1].pos` 量程 `±4π`（16bit 映射 `P_MIN..P_MAX`），分辨率 ≈0.044°；锁位后不会碰回绕
- ⚠️ **`GetPosition()` 返 `angle[now]`，而 `angle[]` 全工程从未被写 → 恒 0**。取角度用 `.pos`
- ⚠️ `ROTATION` 的 `Control_Pantile(0, 0, rc.ch[3])` 第二参 `ch_pitch` 也传 0 → 该模式 pitch 完全不可控，可疑（比赛不用，仅记）

- `XUC` = 协议层：字节流 ↔ 命名物理量。**只做"字节 ↔ 物理量（含单位）"的换算**，不出现 `ctrl`

## 数据链核对（2026-10-05 20:55，用户问"数据链怎么样的"）

**收（视觉 → 云台），4 跳**：
1. 视觉 32B 帧 → UART3（`usart.cpp` DMA+IDLE 中断）→ `xQueueOverwriteFromISR` **整块 100B** 入队

## CRC 三件套审计（2026-10-05 晚，用户问"这三个函数干什么用"）

## 为什么弃用 `RxPacket`（2026-10-05 22:00，用户问）

`xuc.h:26-31` 的 `RxPacket` 只有 `header + checksum`（`sizeof` = 4），**从未描述真实 32B 帧**，是抄来的占位；`memcpy` 它只读到前 4 字节，一个字段都出不来。用结构体映射接收帧另有四笔代价：必须 `packed`、保留字节得瞎编名、位域跨编译器不定、强转是 UB ⇒ 接收侧用**偏移硬解析**（`FR4(m_frame+n)`），发送侧继续 `TxPacket`（我方定义、字段齐全、要 `sizeof` 喂 DMA）。**收发不对称是刻意的，不是遗漏。**

⚠️ **顺带定位一个真坑**：队列 item = `UART_MAX_LEN`(100)，ISR `xQueueOverwriteFromISR(..., m_uartrx, ...)` 拷的是**整个 100B 缓冲快照**，且 IDLE 中断只重装 DMA 计数器**不清零** `m_uartrx` ⇒ 短帧尾部挂着上一帧残字节。**这就是 CRC 必须在读偏移之前跑的理由**（`xuc.cpp:31` 顺序正确，勿调换）。

### 结论 / 坑

- **收发不等长：收 32 / 发 28**，两套帧完全独立（连 header 都不同：收 0xA5 / 发 0x5A）。视觉端若要统一长度得谈。
- **CRC 覆盖范围不同**：收覆盖 0–29（调 `Verify(m_frame, 32)`），发覆盖 0–25（调 `Append(tx_data, 28)`）。**但算法参数一致**（`CRC_INIT = 0xffff`、反射表、低字节在前）✓ 收发都走全局版 `CRC.h`，类内版已注释 ⇒ 无混用风险。
- 队列 item = `UART_MAX_LEN`(100)，**收进来是 100B 快照**，只用前 32。
- 频率：收 = `DecodeTask` 5ms 轮询（`xQueueReceive(..., NULL)` ⇒ timeout=0 非阻塞）；发 = `ArmTask` 100ms = **10Hz**。
- ⚠️ 下行帧 [22..24] 与 [29] 两处保留夹在有效字段中间（`distance` / `fireadvice` / `v_y` 被隔开），是**拼凑协议的痕迹** ⇒ 索要视觉端的逐字节协议表（最好是他那边的 struct 定义）再对一遍。
