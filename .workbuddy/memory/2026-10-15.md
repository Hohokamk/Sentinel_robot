## TIM2 1 MHz µs 时钟源（用户授权改 `tim.cpp` / `tim.h`）

### 改动
- **`tim.h`**：加 `static constexpr uint32_t APB1_TIMER_HZ = 84000000u`（把 `Init()` 里硬编码的 84000000 提成常量，消除重复魔数）；声明 `UsInit()` / `NowUs()` / `UsElapsed()` / `UsDiff()`
- **`tim.cpp`**：实现上述四个函数。`Init()` 里 `84000000` 改用常量

### 🔴 关键决策：**绕开 HAL，寄存器直配**
`HAL_TIM_Base_Init()` 会回调工程里已有的 `HAL_TIM_Base_MspInit()`，而那个函数会 `HAL_NVIC_EnableIRQ(TIM2_IRQn)`（`tim.cpp:87`）。1 MHz 意味着**每秒 1 M 次溢出中断** ⇒ 绝不能开。所以 `UsInit()` 直接写寄存器：`__HAL_RCC_TIM2_CLK_ENABLE()` → `CR1=0` → `PSC` → `ARR` → `CNT=0` → `SR=0` → `CR1=TIM_CR1_CEN`，**全程不碰 NVIC**。
⇒ `TIM2_IRQHandler`（`tim.cpp:47`，`if(phtim[1])` 而 `phtim[1]` 恒为 NULL）永远不会被触发，中断向量表里那条是死的。

### 分频与实测（探针验证）
`f_cnt = 84 MHz / (PSC+1)`，PSC = **83** ⇒ **精确 1.000000 µs/count**（84 = 2²×3×7，1 MHz 整除无余数 ⇒ 无累积量化误差，只有 ≤1 µs 读数量化，远小于 V2 的 2 ms 预算）。
`ARR = 0xFFFFFFFF` ⇒ 回绕 **71.58 min** ⇒ **必须无符号差值 `NowUs() - last`，不能比大小**。
实测边界：`UsInit(0)`→false；`UsInit(1000)`→false（84e6 % 1000 ≠ 0，**拒绝非整除频率**）；`UsInit(100000)`→true（div=840 < 65536，合法）；`UsInit(2e6)`→PSC=41。
探针跑出两处"不符预期"经复核**都是我算错、代码对**：`296+300=596` 而非 396；`div=840` 确实 < 65536。

### 时钟树（`sysclk.h` 核对）
HSE 25 MHz → PLL_M25/N336/P2 ⇒ **SYSCLK 168 MHz**；AHB=DIV1 ⇒ HCLK 168；APB1=DIV4 ⇒ PCLK1 42；**APB 分频≠1 时定时器时钟 ×2 ⇒ TIM2 输入 84 MHz**（与 `delay.Init(168)`、`configCPU_CLOCK_HZ` 自洽）。

### 调用方式（需改 `STM32F405.cpp`，**待用户同意**）
```cpp
timer.Init(BASE, TIM3, 1000).BaseInit();   // 现有：TIM3 @1kHz 给 CanTransimt 分频
if (!TIM::UsInit(1000000)) { /* 停机或降级 */ }   // 新增：TIM2 @1MHz
```
⚠️ **必须在 `SystemClockConfig()` 之后**（依赖 APB1 定时器时钟就绪）。
⚠️ **`UsInit()` 是 static，不需要实例** ⇒ 不要写成 `timer.UsInit()`（虽然也能编过）。

### 后续 A 实验要用它做什么
在 `UART::OnUARTITHandler` 里 `mcu_us = TIM::NowUs()` 打戳，然后与 `system_time` 做**线性回归**：斜率应≈1.0（晶振一致），**残差 RMS = 误差界**（理论下限 1 ms/√12 ≈ 0.289 ms）。RMS ≪ 2 ms ⇒ `time_source=3` / `SAMPLE_TIME_VALID=1`，可进控制。

## 事件四：usart.cpp / usart.h 补时间戳 + 帧长 + 发送守卫（用户授权）

**一句话**：在 IDLE 中断里补上 `rx_time_us`（TIM2 µs 时间戳）和 `rx_len`（NDTR 反推的真实帧长）与丢帧计数，并给 `DMATransmit` 加"上一帧在途就拒绝"的守卫；全工程零 error。**探针实测抓出自己写的帧长公式反了（NDTR 是递减的），已修正。**

### 为什么时间戳/帧长做成 UART 成员而不是队列 item
队列 item 必须是 `UART_MAX_LEN` —— 有 **6 个消费端**（`xuc`/`imu`/`RC`/`judgement`/`supercap`/`power`）都写 `xQueueReceive(*h, buf, ...)`。改 item 长度会一次性改爆 6 个文件（未授权）。而队列是**深度 1 覆盖写** ⇒ 「队列里那一帧」与「本成员」**天然同拍**，语义严格一致。成员声明 `volatile`，32/16 位对齐访问在 M4 上是单条 LDR/STR（原子）⇒ 任务侧不会读到半新半旧。

### 新增成员（public，watch 用）
| 成员 | 含义 |
|---|---|
| `rx_time_us` | 本帧到达时刻（µs，TIM2 @1MHz）。**若 `TIM::UsInit()` 未调则恒为 0** ⇒ 上层可据此判断时基未就绪 |
| `rx_len` | 本帧真实字节数。⚠️ DMA 缓冲不清零，`UART_MAX_LEN` 只能当上限 |
| `rx_cnt` / `rx_drop_cnt` / `rx_overflow` | 帧总数 / **覆盖丢帧数（原来完全静默）** / NDTR 异常次数 |
| `tx_cnt` / `tx_busy_reject` | 成功发起数 / 因在途被拒数 |

### 🔴 NDTR 帧长公式（探针实测纠正）
NDTR **随接收递减**（重装 = 100，每收 1 字节减 1）⇒ **`len = UART_MAX_LEN - NDTR`**。
我第一版写成 `len = NDTR`，探针表格立刻暴露（18 字节的帧算出 len=82）。已修。
实测：18/32/40/64/71/100 字节全部 OK；边界 `NDTR=100→0`、`NDTR=0→100`、`NDTR=0xFFFFFFFF→100 且 ov=1`。
**必须先 `__HAL_DMA_DISABLE` 再读 NDTR**（还在跑时随时在变）。

### DMATransmit 加在途守卫
原实现「无条件 DISABLE→重装 NDTR/M0AR→ENABLE」，在途时重装会把上一帧后半段与本次前半段**拼成一条错乱帧流**，上位机 CRC 必挂且现象是"偶发丢包"（极难查）。
改：判 `NDTR != 0` ⇒ 在途 ⇒ `++tx_busy_reject` 并**返回 false 丢弃本次**。
⚠️ **判据刻意不用 DMA TC 标志位**：`OnDMAITHandler` 只在 `DMA1_Stream4_IRQHandler` 里被调（只有 uart4 的 TX 接了完成回调），其余 UART 靠标志位会永远卡在 busy。读寄存器则始终准确。
⚠️ 返回类型 `void`→`bool`：**现有调用点忽略返回值也能编译，行为不变**（唯一调用点是 `xuc.cpp` 的 `Encode()`）。
参考时序：921600 baud 下 1 B ≈ 10.85 µs ⇒ 46 B ≈ 0.50 ms、64 B ≈ 0.69 ms；正常周期 50~100 ms ⇒ `tx_busy_reject` 应恒为 0，非 0 说明有人极高频调 `Encode()`。

## 事件六：imu.cpp CRC 三处修复 + xuc.cpp 时间戳改真（用户授权）

**一句话**：`imu.cpp` 的 CRC 不只是括号 UB —— 探针实测查出**三个真问题**（`crc` 是成员且清零位置错导致只有第 1 帧能过、无零初始化、`len` 是 `uint8_t` 会被静默截断），已全部修复并加诊断计数；`xuc.cpp` 的 `sample_time_us` 从 `DecodeTask` 时刻近似改为读 ISR 打的真到达时刻（抖动从 0~5 ms 降到传输期的变化），这是 A 实验达 2 ms 预算的最后一步。全工程零 error，两文件**零警告**（`-Wall -Wextra`）。

### 🔴 `imu.cpp` 三个真问题（探针实测，非推理）
| # | 问题 | 实测后果 |
|---|---|---|
| 1 | 🔴 `crc` 是**成员变量**，而 `crc = 0` 写在 `Decode()` CH010 分支的【末尾】——**在 `Check()` 之后** | 每帧从上一帧残值继续累加。探针：第 1 帧通过，**第 2~5 帧全部丢弃** |
| 2 | `crc` 是成员且 `uint16_t crc, len;` **无零初始化**（.bss） | 首帧初值随机 ⇒ 上电后第一帧也可能直接丢 |
| 3 | 🔴 `len` 形参是 **`uint8_t`**，而调用处算出的是 u16 | 帧长 >255 时**静默截断**。探针：len=284 ⇒ 实际只校验 28 字节，其余数据**根本没进 CRC** 却当"校验通过" |
| 4 | `Check()` 缺 `return`（`-Wreturn-type`） | 未知类型时行为未定义 |
| 5 | 🔴 `Decode()` **缺 `if (pd_Rx != pdTRUE) return;`** | 队列空时 `rxData` 保持上次内容 ⇒ **拿旧帧重复解析**，反复刷新 `last_rx_tick`/`init_done` ⇒ 样本有效性判据失真、A 实验统计不可信 |

**修法**：
- `crc` 降为**函数内局部** `uint16_t crc_local = 0x0000u` ⇒ 每帧自复位，不依赖调用方清零、不可能跨帧污染
- 调用处先算 `const uint32_t len_raw = rxData[2] | (rxData[3] << 8)`（**先显式 u16 组合再钳位**），`len_raw == 0 || > sizeof(rxData)-6` ⇒ `++len_bad` 并整帧丢弃
- `Check()` 补 `return false`
- `Decode()` 补 `if (pd_Rx != pdTRUE) return;`
- 新增诊断计数 `rx_ok` / `crc_fail` / `len_bad`（watch 用，A 实验统计通过率靠它）

**探针复验**：连续 8 帧 **8/8 通过**（修复前 1/5）；翻转 payload 任意一位（0/5/20/63）**全部检出**；len=284 **被拦住**。

### `xuc.cpp` 时间戳改真
- `imu_stamp_us` → `frame_time_us`：从 `Decode()` 开头读 `m_uart->GetRxTimeUs()`（**ISR 打的 µs 到达时刻**）
- 新增 `frame_len`，`AppendRx(m_frame, frame_len)` —— **只喂真实长度，不再把整个 100 B 缓冲（含残字节）喂进流式解析器**
- 🔴 `Decode()` 从 `while` 抽干队列改成 **if 单次取**：深度 1 的队列一轮内收多帧时最终只留一帧，取多次会重复累加计数且元信息配对错误
- ⚠️ 仍在同一个 if 分支内**只读一次**元信息：读到一半被 ISR 覆盖会得到「A 帧字节 + B 帧时间戳」的错配
- `GimbalFlags()` 里 `SAMPLE_TIME_VALID` **仍固定 0** —— 诚实标注：现在是"到达时刻"不是"采样时刻"，对应 V2 `time_source=2`，A 实验标定前上位机不得用于基于样本的控制
- 底盘 `0x02` 仍与云台同源 `t_us`（两路 IMU 走不同 UART，没有对应"到达上位机侧"的时刻），已在代码注释里写明

### 编译验证
`imu.cpp` / `xuc.cpp` 均 exit 0；`-Wall -Wextra` 下这两个文件**零警告**（`-Wparentheses`、`-Wreturn-type` 消失）。剩余两个既有小警告：`xQueueReceive` 第 3 参传 `NULL`（应 `0`）、`imu.h` 的死函数 `U2`。

## 事件七：imu.cpp / tim.cpp 收尾清理（用户授权）

**一句话**：把 IMU 解码拆成三个私有分支方法并修掉 IMU601 的**真实越界读**、补上两个分支缺失的 `init_done/last_rx_tick/data_ok`（原代码下 IMU601 和 HI226 的 `IsValid()` 永远 false），给 `UsInit()` 加 `DIER=0`，并清掉 `timer.counter` 这个零消费者的 ISR 空转；探针 22 项全过，ARM 侧零警告。

### 改了什么

| 文件 | 内容 |
|---|---|
| `imu.cpp` | `Decode()` 瘦身为「取帧 + 三路分派」；新增私有 `DecodeIMU601()` / `Decode0x91()`（CH010 与 HI226 **共用**）/ `MarkSampleValid()` |
| `imu.h` | 声明上述三个私有方法；删 `crc`/`len` 成员（改局部变量后零消费者）、死函数 `U2()`、死声明 `getangularvelocitypitch()`；新增 `sample_ok` / `short_payload` 两个诊断计数 |
| `tim.cpp` | `UsInit()` 补 `TIM2->DIER = 0`；`HAL_TIM_PeriodElapsedCallback` 清空（删 `timer.counter++`） |
| `tim.h` | 删 `uint32_t counter` 成员 |

### 🔴 修掉的真 bug

**1. IMU601 分支越界读（真 UB）**
```cpp
Check(rxData, rxData[3] + 4, rxData[rxData[3] + 4])
```
`rxData[3]` 是 `uint8_t`，最坏 255 ⇒ 末下标 **259**，而 `rxData` 只有 100 字节。一帧坏数据越界读 159 字节。

**2. IMU601 分支校验长度算错（逻辑 bug）**
该家族 `len` 是**数据组数**，每组 3 轴 × 2 B = 6 B，数据区是 `len*6` 字节。原代码只累加 `len+4` 字节，覆盖不到 1/6 的数据区 ⇒ 校验形同虚设。已改为 `4 + len*6` 字节求和，校验字节在 `4 + len*6`。

**3. 两个分支不更新有效性标记（分支不对称）**
`IsValid()` 判 `init_done && data_ok && 新鲜度`，但 **IMU601 和 HI226 分支完全没碰这三个变量** ⇒ 切到这两种型号时 `IsValid()` 永远 false（`xuc.cpp` 的 `ORIENTATION_VALID` 会一直挂）。CH010 有、另两个没有，是复制粘贴漏的。现已统一走 `MarkSampleValid()` 收口。

**4. `UsInit()` 未清 `DIER`**
若 TIM2 之前被 `HAL_TIM_Base_Init` 过（会经 MspInit 开 NVIC），残留 `UIE` 会让 1 MHz 计数器每秒进 100 万次 ISR。已补 `TIM2->DIER = 0`。

### 🔴 探针踩到的 `sizeof` 陷阱（值得记住）
初版探针里把解码函数写成 `uint8_t* rxData = s.rxData;`（指针别名），于是 `sizeof(rxData)` = **8 字节**而不是 100 ⇒ `len_raw > sizeof(rxData)-6` 变成 `len > 2`，**所有正常帧全被误判丢弃**（14 项测试红了 13 项）。
真实固件里 `rxData` 是数组成员，`sizeof` 本来是对的 —— 但**这个写法太脆**，已把两处长度上界都改成显式常量 `UART_MAX_LEN - 6` / `UART_MAX_LEN`，任何人以后写成指针都不会静默错一个数量级。

### CRC 口径澄清（避免以后混用）
`imu.cpp::Check` 的注释原来写「CRC-16/MCRF4XX」是**错的**。实际是：
- **IMU `0x5A 0xA5` 帧** = CRC-16/CCITT-FALSE：init `0x0000`、poly `0x1021`、MSB-first、无 final xor、不反射
- **V2 PC 帧**（`CRC.h`）= CRC-16/MCRF4XX：init `0xFFFF`、反射表 `0x8408`、低字节先发

init 都不同、覆盖范围也不同，**别互相当参照物**。

### 新增诊断计数
| 计数 | 含义 |
|---|---|
| `rx_ok` | 帧头 + 长度 + CRC 全过的帧 |
| `crc_fail` | CRC 不匹配 |
| `len_bad` | 长度字段非法 |
| `sample_ok` | **0x91 姿态包**通过 CRC 的帧数 |
| `short_payload` | 0x91 包但 `len < 60`，读不到 yaw 就丢弃 |

⚠️ **A 实验做回归要用 `sample_ok` 当分母，不能用 `rx_ok`** —— 后者含"帧有效但不是 0x91 姿态包"的帧，那些帧没有可用于标定的 `timestamp`。

### `short_payload` 为什么要单独一道
CRC 合法 ≠ 内容够长。`len=20` 的 0x91 帧能通过 CRC，但代码要读到 offset 56 的 yaw（占 56..59）⇒ 需要 payload 至少 60 字节。这道卡在「上界钳位」之后，是独立的一道。

### 探针复验（22 项断言全过）
正常 0x91 帧字段逐项 ✓｜连续 8 帧 8/8 无 crc_fail（回归跨帧累积）｜篡改 payload 一位必检出 ✓｜`len=284` 判 `len_bad` ✓｜`len=20` CRC 合法但被 `short_payload` 拦下且未误标 `init_done` ✓｜`type=0x90` 有效帧计 `rx_ok` 不计 `sample_ok` ✓｜IMU601 `len=250` 判 `len_bad` 未越界 ✓｜IMU601 正常角度帧 `init_done` 正确置位 ✓。

### 🔴 教训一：探针编译通过 ≠ 固件编译通过（我的疏漏）

上一轮我只在 MinGW 上编了「探针」（摘录版逻辑），ARM 侧编的也是探针，**从没编过真正的 `imu.cpp`** —— 而真实 `imu.cpp` 里 `const uint8_t* p` 传给非 const 形参直接炸。

⚠️ `gcc.exe` 是路径带引号的，调用时要加 `@`；`for f in VisualGDB/Debug/*.gcc.rsp` 循环 + `@$f` 即可逐 TU 全编。

### 🔴 教训二：`x * 1000` 不等于把 x 变成高精度

```cpp
// ❌ xuc.h 原实现（编译不过，而且逻辑也错）
uint32_t NowUs() { return (uint32_t)xTaskGetTickCount() * 1000u; }
```
`xTaskGetTickCount()` 是 **1 ms 粒度**，乘 1000 只是把毫秒数值放大 1000 倍，**分辨率仍是 1 ms**。函数名叫 `NowUs` 极具误导性 —— 谁都不会怀疑它偷偷只有 1 ms 精度。
而它恰好用在三处最需要精度的地方：`HandleAim` 的 `age_us` 样本新鲜度判定、`AimReady()`、`AimAgeMs()`。V2 误差预算 2 ms ⇒ 1 ms 量化白白吃掉一半。

**判断法则**：时间源的真实分辨率 = 底层计数器的自增周期。tick 是 1 ms 就永远是 1 ms，换任何乘法都改不了。要 µs 就必须有 1 MHz 的硬件计数器（这里是 TIM2）。

### 🔴 教训三：同一份协议里不能混两套时基

V2 当时有两套时间来源：
| 字段 | 来源 | 分辨率 |
|---|---|---|
| `sample_time_us`（上行） | `usart.cpp` ISR 的 `TIM::NowUs()` | 1 µs ✓ |
| `age_us`（下行判新鲜度） | `xuc.h::NowUs()` = tick×1000 | 1 ms ✗ |

`age_us = now_us - ref_time`，而 `ref_time` 是上位机原样回传的**我们上行那个 µs 值** —— 一个 1 ms 时基减一个 1 µs 时基，差出来的数没有物理意义。
⇒ 统一到 `TIM::NowUs()`。**同一协议内所有时间量必须同一时基，否则相减即无意义。**

### 🔴 教训四：`t_us` 的"降级兜底"会污染 A 实验

```cpp
// ❌ 原实现
const uint32_t t_us = (frame_time_us != 0u) ? frame_time_us : NowUs();
// ✅ 现在
const uint32_t t_us = frame_time_us;
```
`frame_time_us` = ISR 打的**到达时刻**；`NowUs()` = 任务调用时刻（Encode 每 20 ms 跑一次）。兜底让 `t_us` 有时是前者、有时是后者。
⇒ 上位机拿这批数据做**线性回归求恒定延迟**时，混进来的组帧时刻会变成一个**假的截距**（Encode 的 20 ms 周期抖动正好落在残差里），直接把残差 RMS 撑爆 —— 而这正是 A 实验要量的东西。
**时基没就绪就该如实报 0**（TIM2 未使能时 `frame_time_us` 恒 0，上位机看到恒 0 就知道没就绪），而不是悄悄降级到另一个口径。

### 🔴 教训二：「除 CRC 本身外」= CRC 字段不参与计算，不是自同步

手册原文写「CRC校验 = **除 CRC 本身外**其余所有字段(帧头, 帧类型, 长度, 数据域)」，同时给了代码：

```c
crc = 0;
crc16_update(&crc, buf, 4);                // 帧头 2B + 长度 2B
crc16_update(&crc, buf + 6, payload_len);  // 数据域
```

**这是【两段拼接】，中间的 CRC 字段 `buf[4..5]` 被跳过。** 我第一次理解成"覆盖 len+6 整段"（CRC 字段算进去凑自同步）—— 两种理解结果完全不同。样例帧实测：两段拼接得 `0x516C` ✅，整段则对不上。

⇒ 实现上 `Check()` 必须支持**累加器跨调用延续**，所以给它加了 `uint16_t* acc` 参数（传 `nullptr` = 单段从 0 起算）。

### CH010 帧结构（官方确认）
```
[0]    0x5A 帧头
[1]    0xA5 帧类型
[2..3] LEN   u16 小端，数据域长度（不含帧头/帧类型/LEN/CRC）
[4..5] CRC   u16 小端（LSB 低字节在前）
[6..]  数据域
```
**帧总长 = len + 6**（实测 `len=76 ⇒ 82`，与 `rx_len=82` 吻合）。
**算法 = CRC-16/CCITT-FALSE**（poly `0x1021`、init `0x0000`、MSB-first、不反射、无 final xor），与手册 `crc16_update()` 逐位等价。**与 V2 PC 帧的 MCRF4XX 是两个不同算法。**

### 0x91 数据包字段表（偏移相对 `p = rxData + 6`）
| 偏移 | 类型 | 大小 | 单位 | 含义 |
|---:|---|---:|---|---|
| 0 | uint8_t | 1 | - | 标签 `0x91` |
| 1 | uint32_t | 4 | - | ID |
| 4 | float | 4 | Pa | 气压（CH010 无气压计 ⇒ 无意义） |
| **8** | uint32_t | 4 | **ms** | **本地时间戳，A 实验基准** |
| 12 | float | 12 | 1G | 加速度 XYZ |
| 24 | float | 12 | deg/s | 角速度 XYZ |
| 36 | float | 12 | uT | 磁强度 XYZ |
| 48 | float | 12 | deg | Roll(±180) / Pitch(±90) / Yaw(±180) |
| 60 | float | 16 | - | 四元数 WXYZ |

## 事件十：两段 CRC 比较时机写错 —— 我的新 bug（用户报"angle 读不到了"）

**一句话**：上一轮改对了两段 CRC 的覆盖范围，却把"每段各自比较"写成了 `if (!Check(seg)) return;` ⇒ **第一段的中间值必然不等于最终 CRC，第一行就 return，第二段没跑、字段永不更新**。改成 `CrcReset/CrcAccum/CrcResult` 三段接口（只累加、末尾比较一次）修好。

### 🔴 Bug 本体
```cpp
// ❌ 我写的
uint16_t crc_acc = 0;
if (!Check(rxData,     4u,      crc_raw, &crc_acc)) { ++crc_fail; return; }  // ← 这里就 return 了
if (!Check(rxData + 6, len_raw, crc_raw, &crc_acc)) { ++crc_fail; return; }
```
`Check()` 每算完一段就拿自己的结果和 `crc_raw` 比。但第一段算完是**中间值**（样例帧里 `0x035D`），最终 CRC 是 `0x516C` ⇒ 必然不等。

探针复现（官方样例帧）：
```
=== BUG 版本：每段各自比较 ===
  第一段即 return  <- 字段永不更新
  rx_ok=0 crc_fail=1
=== 修复版本：累加后末尾比较一次 ===
  roll/pitch/yaw = 48.7203 / -21.0144 / -45.5118 deg
  rx_ok=1 sample_ok=1 crc_fail=0
```

### 🔴 修法：接口层面防误用
```cpp
CrcReset();                        // 每帧从 0 起算，杜绝跨帧残留
CrcAccum(rxData, 4u);              // buf[0..3]
CrcAccum(rxData + 6, len_raw);     // buf[6..6+len]
if (CrcResult() != crc_raw) { ++crc_fail; return; }
```
三个私有方法**都不暴露比较语义** ⇒ 不可能再写错。`Check()` 恢复成**单段**语义（给 IMU601 算术和校验和将来其他型号复用），头文件和 `imu.cpp` 都写了「别改回每段各自比较」的警告。

### 🔴 我的错误性质（比 bug 本身更值得记）
**这个 bug 的症状和"覆盖范围写错"的症状完全一样**（`crc_fail` 涨 / `rx_ok=0` / `rxData` 有数据但 angle 读不到）⇒ 两次错误互相掩盖，我看到用户报"angle 读不到"时直接以为是覆盖范围没修对，又去改了代码。
⇒ **收到"改了之后出现新症状"的报告，第一反应应该是"我的新改动引入了什么"，而不是"上次没改对"**。尤其是在同一处连续改了两轮之后。

### 教训：探针必须覆盖"多种调用姿势"
这次探针只验证了"两段拼接算得对不对"，没验证"用 `if (!Check(seg)) return;` 的姿势调用会怎样"。**累加器型 API 一定要同时测错误用法**，否则这类 bug 必然漏到实机。

### 最终状态
覆盖范围 = **两段拼接**（`buf[0..3]` + `buf[6..6+len]`，CRC 字段 `[4..5]` 跳过不参与计算），比较 = **末尾一次**。两条都已用官方样例帧 `5A A5 4C 00 6C 51 91...` 验证。ARM GCC 真实 rsp 全编 **18 TU 零 error**，`imu` 零警告。
