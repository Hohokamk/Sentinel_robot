### 底盘硬件事实（用户提供）
- **四轮全向轮**（不是麦轮），**左前起顺时针编号 1 → 2 → 3 → 4**。
- 即：1=左前(FL)、2=右前(FR)、3=右后(RR)、4=左后(RL)。
- 对应关系：`chassis_motor[i]` = `can2_motor[i]` = 拨码 `i+1` = 电机编号 `i+1`（待上机核实）。

### 关键结论：45° X 布局下"全向轮"与"麦轮"逆解同构
独立推导验证（设半轴距 a、半轮距 b，轮心 r=(±a,±b)，驱动方向 d = ẑ×r̂ 切向）：
- d_FL = (1,−1)/√2、d_FR = (1,1)/√2、d_RL = (1,1)/√2、d_RR = (1,−1)/√2 → 与麦轮 X 布局相同
- 逆解矩阵秩 = 3 → **可全向**（用 (2,0,0)/(0,−2,−2c)/(0,0,2c) 三角化验证）
- 力矩独立验证：纯 vy 净力 (0,+2.83)、净力矩 0 ✓；纯 vx 净力 (+2.83,0)、净力矩 0 ✓；纯 ωz 净力 0、净力矩 4×127.3 ✓
- 结论：**K 的取值只影响自转速度手感，不影响"是否走直线/是否纯自转"**（vx/vy 列的力矩和恒为 0，与 K 无关）→ 先取 K=1.0

### 逆解公式（目标轮速，单位 = M3508 反馈的 rpm）
```
1 左前  w1 = vx − vy − K·ωz
2 右前  w2 = vx + vy + K·ωz
3 右后  w3 = vx − vy + K·ωz
4 左后  w4 = vx + vy − K·ωz
```

### 标定指纹（车架空先测"关系"，再落地测"整体方向"）
| 测试 | 期望关系 |
|---|---|
| T1 vx=1000 其余 0 | 4 轮**全同向** |
| T2 vy=1000 其余 0 | 1&3 同向、2&4 同向（**对角成对**），两组相反 |
| T3 ωz=1000 其余 0 | 1&4 同向、2&3 同向（**同侧成对**），两组相反 |

T2 与 T3 的分组方式不同（对角 vs 同侧）—— 这是布局指纹；若两者模式相同，说明轮子不是 45° 布局。
建议用集中符号数组 `const float sgn[4]` 修正，别把负号散落在公式里。

### ⚠️ 本轮发现的真实 bug：RESET 模式会被覆盖
`RC_Control()` 的 RESET 分支（`RC.cpp:135-149`）只写 `can2_motor[i].setspeed = 0`，**不清 `speedx/speedy/speedz`**。
而 `ControlTask`（`taskslist.cpp:132-135`）先跑 `chassis.Update()` 后跑 `rc.Update()` →
- cycle N：chassis.Update() 用**残留** speedx/speedy 写回 setspeed；rc.Update() 再清零 → 周期末为 0
- cycle N+1：chassis.Update() 又用残留值覆盖 → ...

而 `MotorUpdateTask`（2ms）与 `ControlTask`（5ms）无固定相位 → `Motor::Ontimer()` 会采到残留值 → **RESET 模式下底盘仍会以残留指令抖动输出**。
**修法（推荐）**：让 `CHASSIS::Update()` 成为 `chassis_motor[].setspeed` 的唯一写入方 —— 在它内部判 `ctrl.mode == RESET` 则输出 0，并删掉 `RC_Control()` 里那 4 行 `can2_motor[i].setspeed = 0`。

2. **反馈帧**：仲裁 ID = **MST_ID（默认 0）**；`Data[0] = status[7:4] ｜ motor_id[3:0]`；`Data[1:2]=POS`、`Data[3:4]=VEL`、`Data[5:6]=T`、`Data[6]=T_mos`、`Data[7]=T_rotor`。`status`：**0 = Disabled（上电默认）/ 1 = Enabled / 8~E = 过压·欠压·过流·MOS过温·线圈过温·通信丢失·过载**。
3. **问询式反馈**：电机只在收到控制帧之后才周期反馈 ⇒ **不使能也能收到反馈帧**（`CanTransimtTask` 一直在发控制帧），只是电机不出力。这是最安全的"纯接收"测试姿势。
4. 使能/失能/清错/存零 = 仲裁 ID `motor_id`，数据 `FF×7 + FC/FD/FB/FE`。

顺带核实了代码的解析是对的：`State_Decode` 的位切分（POS 16 位、VEL 12 位、T 12 位）与手册一致；ISR 用 `Data[0] & 0x0F` 匹配 motor_id 也正确。

### ⭐ 由此得出的关键结论：现有代码上车是天然安全的

`DMmotor[0].setSpeed` 在 latch 成功前**保持 0**（全局对象零初始化；`PANTILE::Update()` 里 `setSpeed = 1.5f` 那句写在 guard **内部**）→ POS_VEL 下限速 = 0 → 位置规划器不产生运动。

⇒ **即使反馈完全没进来、`setPos` 停在 `init_dm()` 写的 0，Pitch 也只会保持不动**。"朝电机零位转"这个之前反复担心的风险，在这套代码结构下不会发生。

⚠️ 这是**天然保护，不要误改** —— 若把 `setSpeed = 1.5f` 挪到 guard 外面（或给 `DMmotor[0].setSpeed` 填非 0 初值），这层保护立刻消失。

### 结论：问题在 Pitch 电机侧配置

达妙反馈是**问询式**（收到属于自己的控制帧才回）→ **ID 不符会让"发"与"收"两处同时断**，症状就是完全静默，而非数据乱跳。这是"单一根因、双重后果"。

### 三个候选原因（概率排序）
1. **Pitch 的 CAN_ID ≠ 9** —— 改完没保存参数 / 漏改 / 未断电重启
2. **Pitch 接在 CAN1 上** —— 收发全硬编码 `can2`（`taskslist.cpp:108-109`、`DMmotor_transmit` 用 `can2`）→ 收不到 0x109 → 不使能也不反馈
3. **Pitch 的波特率 ≠ 1 Mbps** —— 收不到也发不出

⚠️ 另一变体：Pitch 的真实 ID **也是 6**（两台撞号）→ 两台帧都写进 `jointidata[1]` → Yaw 数据间歇性乱跳。

### 诊断法（推荐，一次定位真 ID）
在 `can.cpp` 加一个全局计数表，在 ISR 的 else 分支统计总线上出现过的**所有**达妙 ID（下标 = `Data[0] & 0x0F`）：

```cpp
// can.cpp 全局
volatile uint16_t dm_id_seen[16] = {0};
// ISR else 分支首行
dm_id_seen[hcan->pRxMsg->Data[0] & 0x0F]++;
// can.h
extern volatile uint16_t dm_id_seen[16];
```

live watch 判读：
- `[6]` 很大 = Yaw ✓
- `[9]` 也大 = Pitch ID 正确 → 转去查 status 位 / 使能 / 故障
- **其它下标有计数 = 那就是 Pitch 的真实 ID**
- 除 `[6]` 外全 0 = Pitch 根本没在总线上说话 → 查接线 / 供电 / 波特率

### 先分清两种"没反馈"
- `can2.jointidata[0][0]` 全程 = 0 → **帧没进来**（电机侧）
- `jointidata[0][0] != 0` 但 `DMmotor[0].pos` 恒 -12.566 → 解析问题（几乎不可能，与 Yaw 同路径）

### ✅ 根因确认（同日 16:06）：Pitch 的达妙挂在 **CAN1** 上

用户回报——**硬件接错总线**。代码收发全硬编码 `can2`（`taskslist.cpp:108-109`、`DMmotor_transmit` 用入参 hcan 但传的是 can2、`DMmotorinit` 同）→ Pitch 收不到 0x109 → 不使能也不反馈。单一根因、双重断链。

### ⚠️ 关键陷阱：`jointpdata` 是 CAN 实例成员（`can.h:44`），**can1 / can2 各一份**

`DMmotor_Ontimer(..., can2.jointpdata[i])` 把编码数据写进 **can2.jointpdata**；而 `DMmotor_transmit(can1)` 读的是 **can1.jointpdata[slot]** → **全 0**。所以：
**只改 `transmit` 的总线参数是不够的，编码目标缓冲必须同步改。** 症状会是"反馈通了但电机纹丝不动"（P_S 下 setPos=0 + 限速 0）。

### 三处必改（全在 `taskslist.cpp`，接收侧不用动）

| # | 位置 | 改动 |
|---|---|---|
| ① | `:89` | `can2.jointpdata[i]` → 按总线选（`dm_bus[i]->jointpdata[i]`） |
| ② | `:108` | `DMmotor[0].DMmotor_transmit(can2)` → `(can1)` |
| ③ | `:158` | `DMmotor[0].DMmotorinit(can2)` → `(can1)` |

`DMmotor[1]`（Yaw）全部保持 can2 不变。

### 推荐写法：一张总线表，一处改完三处自动同步

```cpp
// taskslist.cpp 文件作用域（&can1 是常量表达式，无初始化顺序问题）
static CAN* const dm_bus[2] = { &can1, &can2 };   // DMmotor[i] 所在总线
```

- `:87-89` → `DMmotor[i].DMmotor_Ontimer(DMmotor[i].Kp, DMmotor[i].Kd, dm_bus[i]->jointpdata[i]);`
- `:107-109` → `case 0: for (uint8_t i = 0; i < sizeof(DMmotor)/sizeof(DMmotor[0]); i++) DMmotor[i].DMmotor_transmit(*dm_bus[i]); break;`
- `:157-159` → `for (...) DMmotor[i].DMmotorinit(*dm_bus[i]);`

优点：总线映射只有一处，以后加第三台达妙只改 `dm_bus[]`。

### 接收侧为什么不用改（并且这是个隐式依赖）

`can.cpp:146-151` 的 else 分支**不管帧来自哪条总线，一律 `memcpy(can2.jointidata[i], ...)`** → can1 上的达妙帧照样进 `can2.jointidata[0]`。
所以 `State_Decode(can2.jointidata)`、`motor.cpp`/`control.cpp` 里读 `can2.jointidata[0]` 的 guard、`PANTILE::Update()` 全部保持原样。

⚠️ **隐患**：can1 上现在只有大疆电机帧（0x201~0x208，走 if 分支不碰 jointidata）+ 达妙 Pitch，所以安全。**但以后 can1 若接入 `judgement` / `xuc` / 超电等非 0x201~0x208 的帧，`Data[0] & 0x0F` 有可能撞上 9 或 6，污染 `jointidata`。** 到那时需要给 ISR 加按总线分流。

### 零改动选项

把 Pitch 的 CAN 线从 can1 换到 can2 —— 一行代码都不用改。但 can1 上已有 4 台大疆电机，can2 只有 4 台底盘，**从总线负载看 can2 更空**。若接线方便，换线比改代码干净。
