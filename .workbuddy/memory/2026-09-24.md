## 达妙 CAN 协议 — 已从官方文档核实（2026-09-24）

来源：`https://damiao-motor.jia-xie.com/concept/communication-protocol/` + DM-H6215/J6006/J4310 手册。

| 用途 | 仲裁 ID 规则 |
|---|---|
| 使能/失能/置零/清错（系统命令） | `CAN_ID`（D[7] = 0xFC/0xFD/0xFE/0xFB） |
| MIT 控制帧 | `CAN_ID` |
| POS_VEL 控制帧 | `0x100 + CAN_ID` |
| VEL 控制帧 | `0x200 + CAN_ID` |
| FORCE_POS 控制帧 | `0x300 + CAN_ID` |
| 寄存器操作 | `0x7FF` |
| **反馈帧** | **`MST_ID`（Master ID，默认 0）** |

反馈数据段：`D[0] = ID | ERR<<4`（低 4 位=CAN_ID 低 4 位，高 4 位=状态码 0/1/8/9/A/B/C/D/E），`D[1..2]=POS[15:0]`，`D[3..4]=VEL[11:4]|[VEL[3:0]|T[11:8]]`，`D[5]=T[7:0]`，`D[6]=T_MOS`，`D[7]=T_Rotor`。
→ **`State_Decode` 现有字节拆解是对的，只有 `id` 索引错。**

**结论修正**：`MOTOR_MODE = 0x100` 这个偏移**本身没错**（就是 POS_VEL 模式的规则），错在两处 —— 基数必须是 `this->ID` 而非调用点传的 `1`；VEL 模式应为 `+0x200`（Yaw 用）。使能帧不该加任何偏移，直接 `CAN_ID`。

**Master ID 默认 0 → 两台电机反馈帧撞同一仲裁 ID**，只能靠 `D[0] & 0x0F` 区分。这就是原作者 `if (StdId == 1)` 的本意，但判据写错了。

### `this` 反查下标方案 — 补充细节（用户追问后）
`if (&DMmotor[i] == this)` = "第 i 个元素是不是我自己"。`this` 是成员函数的隐式指针，指向调用者。
**本质**：`ID` 是硬件编号（总线上的名字），数组下标是软件位置，两者无天然关系。原代码 `ID - 0x01` 的错就是把 ID 当中号用。
三种写法：
1. `for` + `if (&DMmotor[i] == this)` — 显式，2 元素时开销可忽略
2. `(this == &DMmotor[0]) ? 0 : 1` — 简单，加电机要改
3. `this - DMmotor` — 指针相减，最简洁；要求 this 必在数组内
**必须补的防御**：`id` 初值设 `0xFF`，循环后判 `if (id == 0xFF) return *this;` —— 否则非数组内的临时对象调用会静默读写 `jointidata[0]`。

## 收尾三件的原理与改法（2026-09-24 23:35 交付，等用户实施）

### ⑥ `vTaskDelayUntil` 为什么基准必须声明在 `while` 外（原理已画时间轴图）
内部逻辑：
```c
xTimeToWake = *pxPreviousWakeTime + xTimeIncrement;   // 拿"基准"加周期，不是拿 now 加
*pxPreviousWakeTime = xTimeToWake;                    // 写回，留给下一轮
if (xTimeToWake > xTickCount) vTaskDelay(xTimeToWake - xTickCount);
```
三个要点：
1. 第一个参数是**指针（入参兼出参）**，函数要往里写 —— 它保管的是"上一轮应当醒来的绝对时刻"。
2. 语义是"睡到 `基准 + 周期` 这个**绝对刻度**"，不是"睡 N 个 tick"。
3. 因此基准必须**跨轮存活**。声明在 `while` 内 → 每轮都是新变量、初值 = 当前时刻 → `基准 + 2ms` 恒等于 `now + 2ms` → **完全退化为 `vTaskDelay(2)`**。

后果：实际周期 = 2ms + 本轮执行时间，每次抖动被永久累加 → 漂移只增不减，无自愈机制。

本项目后果加重的原因：
- `CanTransimtTask` 用 `(timer.counter++) % 3` 做三态轮转，**正确性依赖调用频率稳定**；周期一抖，三种帧间隔不均 → M3508 电流帧不匀 → 电机啸叫 / 低速抖动。
- `MotorUpdateTask` 与 `CanTransimtTask` **同为优先级 2**，时间片抢占使两者执行时间互相影响，漂移叠加。

**改法**：`taskslist.cpp:80` 整行 `TickType_t xlastWakeTime = xTaskGetTickCount();` 上移到 `while` 之前；`:101` 的 `xlastWakeTime1` 同理。函数体其余不动。

## `xlastWakeTime1` 已移出 + 暴露的理解缺口（2026-09-24 23:44）

用户已把 `CanTransimtTask` 的 `xlastWakeTime1` 提到 `while` 外，但**加的注释说明他还没真正理解**：

> `//不知道为什么要从while里面挪出来，这个函数是FreeRTOS的一个函数，获取当前任务的时间戳`

→ 他的困惑点是：**`xTaskGetTickCount()` 的位置为什么会影响 `vTaskDelayUntil` 的行为？** 说明上一轮讲的是"基准被重置"，而他关注的是"这一行取时间戳"这个动作。

**下次讲这个知识点，从「写回」切入，不要从「漂移」切入：**
`vTaskDelayUntil` 会把 `*pxPreviousWakeTime` **改写**成 `*pxPreviousWakeTime + 周期`，然后睡到那一刻 —— 它需要这个变量**记得上一轮的计划**。声明在 `while` 内 → 变量每轮重新诞生、初值 = 现在 → 函数算出的永远是 `现在 + 周期`，与直接调 `vTaskDelay(周期)` 等价。
**类比（更直击）**：`vTaskDelayUntil` 是一个"响完会自己往后拨"的闹钟；把它放在 `while` 里，等于每次响完就把闹钟扔掉、换个新的重新对时到"现在"，它永远只知道"从现在起 N 毫秒"。

已给用户可替换的注释文案：
`// 基准须跨轮存活：vTaskDelayUntil 会把下次唤醒时刻写回此变量，声明在 while 内每轮被重置，退化为 vTaskDelay`
