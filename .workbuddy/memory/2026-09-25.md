## `CONTROL::Init()` 崩溃问题逐行核实（用户指定优先解决）

### 调用路径（`STM32F405.cpp:92–103`）
```cpp
ctrl.Init({ &can2_motor[0..3] });   // 第 1 次：4 台全是 chassis
ctrl.Init({ &can1_motor[0..3] });   // 第 2 次：shooter, shooter, supply, pantile
```

### 崩溃点 1 —— `control.cpp:30`（第 1 次调用就触发）
`pantile_motor[PANTILE::TYPE::PITCH]->setangle = para.initial_pitch;`
`PANTILE::TYPE { YAW, PITCH }` → YAW=0 / PITCH=1 → `pantile_motor[1]`。
第 1 次调用的 4 台全是 `chassis`，`pantile_motor` 一个都没填 → 全 nullptr → 写 0 地址附近 → HardFault。

### 崩溃点 2 —— `control.cpp:23`（第 2 次调用触发）
```cpp
case(function_type::supply):
	supply_motor[num4]->spinning = false;      // :23 先解引用
	supply_motor[num4]->need_curcircle = false;// :24
	supply_motor[num4++] = motor[i];           // :25 后赋值
```

**顺序错误**：指针还没赋进去就解引用它。

### ⚠️ 更正之前的错误结论
`supply` 分支缺 `break` **不是崩溃原因**：它 fall through 到 `default`，而 `default` 体只有 `break` → 等效 no-op。属规范问题（`-Wimplicit-fallthrough`），非故障。
（MEMORY.md 已同步更正。）

### 根因（光修空指针不够）
1. **云台只有 1 台标 `pantile` 的 `Motor`**，但 `pantile_motor[]` 需要 YAW+PITCH 两槽 → 判空只能止血，PITCH 永不初始化。
2. **达妙不进 `Motor` 体系**：`DMMOTOR` 是独立类（无继承、不在 can1/can2 数组里），`CONTROL::Init(vector<Motor*>)` 根本收不到。而云台的 Pitch/Yaw 命名恰好指向达妙那两台。
3. `control.h:64` `void init_dm();` **只有声明、无定义、无调用** —— 原作者给达妙预留的钩子没写完；`control.h:11` 的 `init_DM` 成员同样未使用。
4. **`num1..num4` 是局部变量** → 每次调用从 0 重来，"多次调用追加"的语义退化成"覆盖"（当前因为两批 function_type 不重叠才没暴露）。

### 结构性疑点：下标语义 vs 填充逻辑
`pantile_motor[num2++] = motor[i]` —— `num2` 是"第几个遇到的 pantile"，而下标语义是"哪个轴（YAW/PITCH）"。
唯一那台 M6020 会被放 `pantile_motor[0]` = **YAW 槽**；若它实际是 Pitch 轴则槽位错。
**`Motor` 类没有任何字段可区分轴**（只有 `function_type::pantile`）→ 这个映射无法从代码推导，必须人为指定。

### ✅ 达妙协议核实（WebSearch 官方文档，2026-09-25）
三种控制帧的 Kp/Kd 归属：

| 模式 | 仲裁 ID | 数据段 8 字节 | Kp/Kd 是否在帧内 |
|---|---|---|---|
| MIT | `motor_id` | p(16) v(12) **kp(12) kd(12)** t(12) | **是**，每帧下发 |
| POS_VEL | `0x100+motor_id` | float 位置 + float 速度（**v_des = 梯形匀速段速度，即限速**） | **否** |
| VEL | `0x200+motor_id` | float 速度 + 4 字节 0 | **否** |

结论（回答用户"达妙 PID 在哪"）：
- 本机 Pitch=P_S / Yaw=SPEED → **两种模式都不带 Kp/Kd** → `DMMOTOR::Kp=10/Kd=0.6` 在当前配置下是**死参数**（只有 MIT 分支才会打包进帧）。
- 参数在**达妙上位机**里配（或用出厂默认）。**达妙不会"自己调参"**，不存在自动整定。
- 顺带核实的两个特性：**上电默认 Disabled**（必须发 0xFF...0xFC 使能帧，仲裁 ID = motor_id）；**通信丢失保护**（CAN 命令超时自动退出使能）→ `ArmTask` 每 100ms 重发使能**不是冗余，是必需**。
- 反馈帧仲裁 ID = `MST_ID`（reg 7，默认 0），D[0] = `status[7:4] | motor_id[3:0]` → 印证 `can.cpp` 里用 `Data[0] & 0x0F` 认电机的写法正确 ✅；status 码 0x0=DISABLED / 0x1=ENABLED / 0x8~0xE=各类故障。

| 0 | **累加**：`m_error[INTEGRATE] += error`（读-改-写） | **覆盖**：`m_error[LLAST] = m_error[LAST]*0.92f`（**先写后读**） | ❌ **冲突** |

| 2 | 本次误差 `e(k)` | 本次误差 `e(k)`（带 1.08 缩放） | ✅ |

⚠️ **更正上一轮的说法**：我原说"`Delta()` 会读到 `Position()` 留下的积分值"——**不准确**。`Delta()` 第一行就覆盖槽 0，读之前已写，所以它**不会被积分值污染**。
真正的问题是**反向**：`Position()` 的积分器依赖槽 0 的历史值（`+=`），而 `Delta()` 每轮把槽 0 重置成 `e(k-1)*0.92`（误差量级的小值）→ **交替调用时积分器永远累积不起来**，`Ti` 项实质失效。

→ **结论不变，但性质要说准：这不是 bug，是"使用约束"。** 作者的取舍是"两种算法共用一块 3 元素数组省 4 字节"。`enum` 里同值不同名，**编译器不警告**，这才是危险点。
→ **规则**：一个 PID 对象锁死一种算法，永不交叉。`pid[position]` 永远 `Position()`，`pid[speed]` 只用一种。
→ 串级（原作者意图）时两个对象**各用各的算法**，天然安全：位置环用 `pid[position].Position()`、速度环用 `pid[speed].Delta()`。
→ 彻底解耦的可选项：`m_error[3]`→`m_error[4]` 且 `LLAST = 3`（只改 `pid.h` 内部，`m_error` 虽 public 但外部无访问）。

   → 1.08×0.92=0.9936 近似抵消，e(k-2) 额外衰减 0.92（轻微泄漏）。**整定不要按公式算增益。**

## 第九轮：更正 mode 结论 + 初值时机分析（2026-09-25 17:07）

### ⚠️ 重要更正：`control.h:18` 的 `mode` **不是不定值**
上一轮我写的「`mode` 无初值 → 上电到遥控信号之间是不定值」**错误**，必须更正：
- `CONTROL ctrl;`（`STM32F405.cpp:71`）是**全局对象** → 静态存储期 → C++ 标准保证**先零初始化**再运行构造函数。零初始化把 `mode` 置 0。

- **"不定值"只适用于局部变量**；全局/静态存储期的标量全部零初始化。
→ 结论方向不变，但性质要改：不是「垃圾值走到错误分支」，而是「**mode=PC 落在保护范围之外**」。

### 真正确认的危险路径（逐环节可指位）
```
上电 → mode = PC(0)
遥控未连接 → rc.s[0] = rc.s[1] = 0（rc 亦为全局对象，零初始化）

```
→ 所以 `RC.cpp:152`（`setangle = angle[now]`）**只在「遥控器已连 + 拨码命中 RESET」时生效**。

### 时机分析：为什么不能把初值直接写成 `angle[now]`

```cpp
// motor.cpp 解析反馈、写 angle[now] 之后：has_feedback = true;
```

两个 bool 语义分开：`has_feedback` = 电机层面「收到过数据」；`angle_latched` = POS 层面「目标已钉」。
**判据必须是「收到反馈」这个硬件事实，不能用「任务启动后等一会儿」这种时间猜测。**

**折中（不加成员，用哨兵值）**：`control.cpp:46` 写 `setangle = -1.f;`（编码值不可能为负），POS 分支 `if (setangle < 0.f) setangle = angle[now];`。缺点：语义靠约定；且 CAN 一直不通时 `angle[now]` 恒 0，仍会往 0 冲 → 不完整。

## 第十轮：has_feedback / angle_latched 的置位点与判据（2026-09-25 17:40）

用户问：`has_feedback` 置位写在 `motor.cpp` 写完 `angle[now]` 之后对吗？`angle_latched` 哪里要用？

### ⚠️ 更正第九轮的一处错误建议
第九轮我给的形态里写了 `if (!has_feedback) return;` —— **错误，必须更正**。
POS 分支（`motor.cpp:122-129`）**位于公共尾段之前**，`return` 会跳过 `:130-135`：
| 被跳过的行 | 后果 |
|---|---|
| `:132 angle[pre] = angle[now]` | `angle[pre]` 永不更新 → `angle[now]-angle[pre]` 恒 0 → `curspeed` 恒 0、`recorded_the_Laps()` 永不累积、`distance` 恒 0 |
| `:134-135` odata 回填 | 该 slot 的 CAN 字节保持上一帧残留值，不会被清零 |
→ 正解：用 `if/else` 结构表达「未就绪就憋住输出」，**绝不能在 mode 分支里 return**。

### `has_feedback` 置位点与判据
**位置**：`motor.cpp:77`（`temperature` 赋值）之后、`mode` 分支（`:99`）之前。

**判据（关键：不能裸写 `= true`）**：`Ontimer` 由 `MotorUpdateTask` 每 2ms 无条件调用，`idata` 是**常驻缓冲**（`can1.data[12][8]` / `can2.jointidata`），没收到帧时读到的是旧值/零。裸写会在第一次调用（上电、无任何 CAN 帧、全零）就置位 → latch 到 `angle[now]=0`。

候选判据对比：

| 判据 | 可用? | 说明 |
|---|---|---|
| `idata[idx][6] != 0`（温度非 0） | ✅ **推荐** | 真帧温度必在 20~70；上电缓冲全 0。**失败方向安全**（偶发 0 只是晚 1ms latch，不会错误 latch） |
| `angle[now] != 0` | 🔶 可用 | 更贴语义，但编码值 0 是合法位置（1/8192）→ 会卡住 |
| `getStatus() != UNCONNECTED` | ❌ **不可用** | `StatusIdentifier` 的 `disconnectCount` 从 0 递增到 `disconnectMax=20` 才算失联，**前 19 帧一律返回 `FINE`** → 误判为「有反馈」→ 过早 latch → 危险方向 |
| ISR 侧接收计数 | ✅ 最严格 | `can.h` 加 `volatile uint32_t rx_cnt[8]`、ISR `++`；但 `Motor` 拿不到总线对象 → 需注入 `CAN*` 成员，改动面大。**留作跑通后的重构** |

### `angle_latched` 的使用面
**只在 `Motor::Ontimer` 的 POS 分支内，用两处**（判据 + 门控）。SPD / ACE 分支不需要（速度环不存在「目标位置从哪起步」）；`control.cpp` / `RC.cpp` **不用碰**。

推荐形态（`motor.h` 的 bool 加在 `:59` 附近，初值 `false`）：
```cpp
else if (mode == POS)
{
    if (!angle_latched && has_feedback) { setangle = angle[now]; angle_latched = true; }
    if (angle_latched) { /* 第一版这里只跑内环 */ }
    else               { current = 0; }   // 未 latch → 憋住
}
```

### 四个必须知道的点
1. **两个 bool 都是一次性 latch，置位后永不复位**。若做成每帧刷新 → 丢一帧就重新 latch → 目标跟着电机跑 → 位置环永远追不上（电机不动或缓慢爬行）。
2. **`angle_latched` 一旦生效，`para.initial_yaw = 4900` 的风险自然消解** —— latch 在第一次真帧时执行，早于任何 PID 输出，把 `ctrl.Init()` 写的 4900 覆盖掉。这就是 latch 方案的全部价值。
3. **`RC.cpp:152` 与 `angle_latched` 无耦合**：RESET 把 `setangle` 写回 `angle[now]` 只是「手动 re-latch」，`angle_latched` 保持 true 不影响；反之若 latch 未完成，RESET 写 0 也会被随后的 latch 覆盖。**不需要在 RC 侧置位/清位。**
4. **`current = 0` 在未 latch 时必须显式写**：`current` 是上一次的值，不写就可能在接上外环后把残留值发出去。
   （另：`current` 是 `int32_t`，`Delta()` 返回 float → 隐式截断，对电流量级无所谓。）

## 第十一轮：M6020 索引链条核实 + "写死限位值"可行性（2026-09-25 17:46）

用户问：「可以直接测量出限位所在的编码，然后直接给一个可用的默认值吗？」

### ✅ 可行性结论（WebSearch 官方手册核实）
GM6020 官方手册：反馈 DATA[0:1] = **rotor mechanical angle**，0~8191 ↔ 0~360°，1kHz。
→ **绝对式磁编码器，断电重启不丢失**（CSDN 交叉印证）→ 同一物理位置每次上电读数相同 → **写死有效**。
⚠️ **`sum_angle` 不能写死**：`recorded_the_Laps()` 累积，0 点 = **上电位置**，每次上电不同。
→ 实测必须读 `angle[now]`；与用户已定的"误差基准 = `angle[now]`"正好统一。

### ⚠️⚠️ 重大发现：M6020 索引链条要求「拨码开关 = 1」
`enum { ID1 = 0x205, ID2, ..., ID8 }` → `IDn = 0x204 + n`，`IDn - ID1 = n - 1`（index 载体）。
`can1_motor[3] = Motor(M6020, POS, pantile, ID5, ...)` → `this->ID = 0x209` → index = **4**。

| 环节 | 公式 | 落点 |
|---|---|---|
| 接收 ISR `can.cpp:141` | `data[StdId - 0x201]` | index 4 ← **StdId 必须 = 0x205** |
| 取值 `motor.cpp:66` | `data[ID - ID1]` = `0x209-0x205` | `data[4]` ✅ 自洽 |
| 发送 `motor.cpp:134-135` | `odata[4*2]=temp_data[8],[9]` | 落在 `taskslist.cpp:112` 的 **0x1FF 帧字节 0-1** |

GM6020 StdId = `0x204 + 拨码ID`；0x1FF 帧字节 0-1 = **ID1 的槽**。
→ **收发两侧一致的前提都是「M6020 拨码 = 1」**（不是 5）。

**若拨码 = 5，三个后果**：
1. StdId = 0x209 > `can.cpp:139` 的 `id <= 0x208` 上限 → 落进**达妙分支** → `can1.data[4]` 永远为 0 → `angle[now]` 恒 0 → **测出的"限位"全是 0**
2. 角度高字节低 4 位 = 9 时（≈12.5% 位置，angle∈[2304,2559]∪[6400,6655]）该帧被写进 `can2.jointidata[0]` —— **达妙 Pitch 的槽** → 污染达妙反馈。（低 4 位 = 6 时同理污染 Yaw）
3. GM6020 ID5 只认 **0x2FF** 帧，代码只发 0x1FF/0x200 → **收不到控制帧，永远不动**

→ **测量前第一件事：核实拨码开关**。（`motor.cpp:69-72` 那个被注释的 `if (M6020) trainsmit_or_receive_ID += 4;` 是另一套索引方案的残留 —— 用它会得到 index 8，`odata[16]` 越出 `temp_data[16]`，**别启用**。）

### 测量方法论（已给用户）
1. 测量时电机**必须通电**（要发反馈帧）但**绝不能输出电流** → 现在 POS 分支空、`current` 恒 0 → 天然安全 ✓
2. 推到两端记 `a1` / `a2`（读 `angle[now]`，不读 `sum_angle`）
3. 行程宽度 = `getdeltaa(a2 - a1)`，应 ≈ ±4096 → **顺带验证"180° 行程"这个前提**
4. **`initial_yaw` 要的是中点，不是端点**，且跨 0/8192 边界时不能直接取算术平均：
```
delta = getdeltaa(a2 - a1);   initial_yaw = a1 + delta / 2.f;   // 再对 8192 取模回绕
```
（若 `a1=7600, a2=500`，直接 `(a1+a2)/2 = 4050` 是**反方向**的中点 → 接外环后全速顶反方向。）

### "写死初值" vs latch —— 职责不同，不可互替
| 需求 | 靠什么 |
|---|---|
| 开机第一帧不飞向错误位置 | `initial_yaw` 实测值 **或** latch（二选一） |
| `setangle` 被设到行程外时不顶死烧电机 | **限位钳制**（写 `setangle` 处 clamp）—— 写死初值做不到 |
| 换电机 / 上位机零位校准 / 编码器受扰漂移 | **只有 latch 能自适应** |

**时序事实（`STM32F405.cpp` 实读）让 latch 几乎零风险**：
`:82-83 can1/can2.Init()`（CAN 中断开始收帧）→ `:94/100 ctrl.Init()`（写 `setangle = initial_yaw`）→ `:107 task.Init()`（FreeRTOS 才启动）

→ 有 latch ⇒ `initial_yaw` 退化为纯占位符（从头到尾没机会驱动电流）。
→ M6020 未接好 ⇒ `idata` 全零 ⇒ 不 latch + `current = 0` 门控 ⇒ 也安全。**双向都安全。**

**行为差异（需用户定）**：有 latch → 上电后云台保持不动；无 latch → 上电后自动转向中点。

1. 核实拨码 = 1（否则后续全是白干）
2. 实测 `a1`/`a2` → `getdeltaa` 取中点 + 验证行程
3. `para.initial_yaw` 改实测中点（次要收益）
4. **新增 `para.yaw_min` / `yaw_max` → `PANTILE::Update()` 写 `setangle` 前 clamp**（真正的安全网）
5. latch 保留（4 行，自动适配漂移）

## 第十二轮：用户"拨码不就是 ID 吗"+"latch 是什么"的概念澄清（2026-09-25 19:12）

### 澄清 1：`ID5` 这个名字 ≠ 拨码 5（命名陷阱）
已用图讲清。核心：**两个电机家族的反馈 ID 基址差 4**
| 家族 | 反馈 ID | 控制帧 |
|---|---|---|
| C620/C610（M3508/M2006） | `0x200 + 拨码` | 拨码1-4 → 0x200；5-8 → 0x1FF |
| GM6020 | `0x204 + 拨码` | 拨码1-4 → **0x1FF**；5-7 → **0x2FF** |

代码的 `IDn - ID1 = n-1` 下标体系是**按 C620 设计**的（C620 拨码 n → 下标 n-1 ✅）。
GM6020 下：拨码 n → 下标 `n+3`。要它 = 4 → **n = 1**。
→ **`ID5` 对 M3508 是"拨 5"，对 GM6020 是"拨 1"。** 用户那台必须拨 **1**。

### 澄清 2：latch 概念（用户完全没接触过这个词）
latch = 门闩/锁存 = "把某个瞬间的值锁住，之后不再动它"。
- 三阶段：① 上电 `setangle = 4900` 但门控关着（`current = 0`）→ ② **首帧真反馈 → `setangle = angle[now]`，锁存一次** → ③ 之后 `setangle` 归遥控器 / `PANTILE::Update()` 管
- **必须配 bool**：否则每 2ms 都写 `setangle = angle[now]` → 目标永远等于当前位置 → 遥控指令被吃掉 → 云台像被粘住不动
- 类比：电梯上电不知道轿厢在哪层，先读当前层当目标 → 不动，等按键。若每秒重读一次当前层当目标，电梯永远到不了任何楼层
- 与"写实测初值"的关系：**安全性等价**（都不会往行程外顶），区别只在开机行为（写死 → 自动转向中点；latch → 原地不动）+ 抗零位漂移能力

## 第十三轮：「偏移 4」的方向定案 + latch 完整写法（2026-09-25 19:22）

### ✅ 用户想起来的"拨码要偏移 4" —— 方向已澄清
**公式：`IDn` 里的 n 比 GM6020 实际要拨的号大 4 → 拨码 = n - 4。**（不是"拨码 + 4"）

三步推导：
1. 反馈 ID 基址：C620/C610 = `0x200 + d`，GM6020 = `0x204 + d` → **差 4**
2. `can.cpp:141` 的接收下标写死 `StdId - 0x201`（0x201 = C620 基准）
3. 代入：C620 拨码 d → 下标 `d-1`；GM6020 拨码 d → 下标 `d+3` → **同下标下 GM6020 拨码小 4**
4. 代码 `IDn` → 下标 `n-1`；要 `n-1 = d+3` → `n = d+4` → `d = n-4` ✅

### 完整映射表（决定"哪几个下标能装 GM6020"）
| 下标 | 枚举名 | C620/C610 拨码 | GM6020 拨码 | 控制帧 |
|---|---|---|---|---|
| 0-3 | ID1-ID4 | 1-4 | **不可用**（GM6020 不认 0x200 帧） | 0x200 |
| 4-7 | ID5-ID8 | 5-8 | **1-4** | 0x1FF |
→ **GM6020 只能装下标 4-7（`ID5`-`ID8`），拨码 1-4**。本机 M6020 用 `ID5` → **拨 1**。
→ GM6020 拨码 1-4 的反馈 StdId = 0x205-0x208，全部 ≤ `can.cpp` 的 0x208 上限 ✓；发送落 `temp_data[8..15]` = 0x1FF 字节 0-7 = GM6020 ID1-4 ✓ **完全自洽，零代码改动**。

## 第十五轮：用户把"掉线保护"误读成"掉电保护"+"只能用一次"（2026-09-25 19:50）

### 用户的两个误解（已纠正）
1. **是"掉线"，不是"掉电"** —— 指 CAN 通信中断 / 电机失联（拔线、接触不良、电机烧、总线短路），与供电无关。
2. **"一次性"≠"整机只能用一次"** —— 指 `has_feedback` / `angle_latched` 两个 bool 在**一次上电周期内**只置位一次、之后不复位。每次复位（NRST 或断电重启）→ 全局对象重新零初始化 → 两 bool 回 `false` → 全套重来。**烧录一次可无限次运行**；想"重新对准"按复位键即可，不必重烧（另有 `RC.cpp:152` 的 RESET 模式做手动 re-latch）。
3. **不复位是 design 不是 defect**：若 bool 每帧复位 → 遥控把云台转走后下一帧 latch 又拉回 → 指令被吃掉 → 云台像被粘住。

### 掉线失效链（用户关心"为什么现在没保护"）
① CAN 断线 → ② `can1.data[4]` 停止更新（`Ontimer` 由 `MotorUpdateTask` 每 2ms **无条件**调用，读到的是常驻缓冲旧值）→ `angle[now]`/`curspeed` 冻结 → ③ POS 环照常算、继续输出电流 → ④ **线接回的第一帧 `angle[now]` 从冻结值跳到真实值 → `err` 突增 → PID 输出瞬间打到限幅 → 云台猛弹**（唯一暴露时刻，且是冲击不是渐变）。
补充：GM6020 反馈与指令走同一根 CAN 线 → 线断时电机既收不到反馈也收不到电流 → **它是自由的（无力）**，最大物理风险是 Pitch 受重力自己掉下来。

### 为什么"现成机制"没生效（本轮 grep 实证）
- `motor.cpp:40-59` `StatusIdentifier` + `motor.h:50` `getStatus()` 就是原作者为掉线写的，**但全工程无任何调用点** → **彻底死代码**。

### 结论与优先级
这一阶段**不做**掉线保护。真正该做的是**限位钳制**（防烧电机的唯一有效手段）。掉线保护属"跑通之后的重构"，最小实现 = 帧计数/时间戳（`can.h` 加 `rx_cnt[8]`，ISR 里 `++`，`Ontimer` 比较本帧与上一帧计数）。

## 第二十二轮：⚠️ 编译错误 C2352「非静态成员引用必须与特定对象相对」根因与改法（2026-09-25 23:10）

| `PANTILE::TYPE::YAW` | PANTILE 内嵌枚举 | ✅ |
| `para` / `DMmotor` / `can1_motor` / `can2_motor` | 全局对象/数组 | ✅ |

- **首帧无冲击已核实**：latch 当帧 `setangle = angle[now]` → err = 0 → `Position(0)` = 0（INTEGRATE 累加 0、导数初值 0）→ speed_ref = 0 → `Delta(0 - curspeed)` ≈ 0 ✓
- **M6020 的 PID 实参**（`STM32F405.cpp:36`）：`PID(100.0f, 0.02f, 0.0f, 0.f)` = 内环；`PID(1.0f, 0.0f, 0.5f, 0.7f)` = 外环（Kp=1, Ti=0, Td=0.5, α=0.7）
- ⚠️ **`PID` 构造签名是 `(Kp, Ti, Td, alpha)`** —— 第二参是 **Ti（积分时间）不是 Ki**。外环 Ti=0 → 积分项恒 0 → `Position(err, 1000.f)` 的第二参**完全无效**（它钳的是积分槽，不是输出）。

### ⚠️ 新识别的首要风险：`Delta()` 的稳态行为是积分器
代入 `Delta()` 实现（`pid.h:35-42`，含 0.92 泄漏、×1.08）求稳态：
`Δcurrent ≈ (Kp·0.0864 + Ti·1.08) · e` （每 2ms 周期）
→ M6020 内环 Kp=100：**1 rpm 稳态误差 ⇒ current 每周期 +8.66，约 3.5 s 爬到 maxcurrent=30000**。
- 正常收敛时无害（e→0 即停）
- **危险组合 = 目标速度不可达**：撞机械限位 / 堵转 → e 恒非零 → current 一路到 30000 → **满电压堵转**
- **限位 clamp 挡不住这条**（它管"目标角越界"，不管"内环追不到目标速度"）
- 位置环输出上限 ±200 rpm；83° 行程在 83 rpm 下约 0.3 s 走完 → 撞限位很快

### 推进顺序（4 步，每步可独立上机）
1. **底盘能动**：麦轮逆解（一般式 `FL=vx-vy-Kω` / `FR=vx+vy+Kω` / `RL=vx+vy-Kω` / `RR=vx-vy+Kω`，`K=(半轴距+半轮距)/轮半径`）。**符号必须三项标定**（只给 vx → 应直行；只给 vy → 应纯平移；只给 ωz → 应原地自转），网上每张表约定都不同，包括我给的那张。标定时**车架空**。
2. **云台 yaw 能转**：`yaw_ready` bool + `mark_yaw = yaw->angle[now]` 首帧 latch，之后 `setangle = ClampAngle(mark_yaw + delta_yaw, center, span)`。
3. **达妙两轴**：Pitch P_S 发 `setPos`(弧度，钳 ±4π)+`setSpeed`；Yaw SPEED 发 `setSpeed`(rad/s，钳 ±10)。**Pitch 同样有开机 latch 问题**（`dm_initial_pitch=0` 会让它上电转零位）→ 用 `DMmotor[0].GetPosition()` 取基准。先确认 `can2.jointidata` 有真反馈，否则 latch 锁到 0。
4. **射击**：`shooter_motor[]->setspeed = shoot_speed`（6000 偏高，先 3000）+ `supply_motor[0]->setspeed`。SPD 单环 = **按住连续转**，不是一格一格；`pd`/`spinning`/`need_curcircle` 是给 `ACE` 分支的，往后放。
