## `Keep_Pantile` / `Keep_Direction` 语义厘清与设计（用户逐个解决，2026-10-09）

### 两个函数的定位（同一问题的两面）

| 函数 | 执行器 | 做什么 | 触发场景 |
|---|---|---|---|
| `Keep_Pantile` | **云台** | 让枪口保持指向某方向 | 底盘转动/被撞时，云台反向补偿 |
| `Keep_Direction` | **底盘** | 让底盘的动作以云台为参考系 | 云台朝向 ≠ 车头朝向时，摇杆方向跟着换 |

直觉：**底盘转了 ⇒ 云台补（Keep_Pantile）；云台转了 ⇒ 底盘动作换参考系（Keep_Direction）**。

### ⚠️ `Keep_Direction` 名实不符（关键）

`RC.cpp:140` 的 FOLLOW case 注释写的是"按照云台的角度来计算出 speedx 和 speedy，以云台的角度为参考系" = **底盘跟随云台方向移动**；但函数名叫 `Keep_Direction`（保持方向）。**实际要实现的是"跟随"不是"保持"**，建议改名 `Follow_Pantile`。

### 现状

- **`Keep_Pantile`**：空实现 + **零调用**（全工程 grep 只有声明和定义）。且它若写 `pantile_motor[YAW]->setangle` 会成为**第三个写者**（另有 `Control_Pantile` 第1段 与 `OnPC()`）⇒ 必须挂**专属模式**，而 `CONTROL::LOCK` 正是为此预留的死枚举
- **`Keep_Direction`**：空实现，但 `RC.cpp:140` 的 FOLLOW 模式（左拨中+右拨上）**会调它** ⇒ 该 case 先 `speedx/speedy=0` 再调空函数 ⇒ **FOLLOW 模式底盘永不动**（真 bug）

### `Keep_Pantile` 实现要点

用 `imu_pantile`（装在**发射头**）做闭环 —— 它的 `GetAngleYaw()` 就是**枪口世界朝向**，无需坐标变换：
```cpp
const float err = ctrl.GetDelta(angleKeep - frameOfReference.GetAngleYaw());
if (fabsf(err) < KEEP_DB) return;
y->setangle += KEEP_KP * err * (8192.f / 360.f);
```
- 签名里的 `IMU frameOfReference` 是**按值传递**，会整块拷贝 `rxData[100]` ⇒ 改 `IMU&`
- IMU 输出范围确认：`imu.cpp` 的 `angle.yaw = getword(...) * 180 / 32768` ⇒ **±180°**，与 `GetDelta` 归一化区间一致 ✓
- ⚠️ IMU 装在发射头上会**跟着 pitch 转**，pitch 远离 0 时有欧拉角耦合误差（行程 -31.5°~+22.9°，量级可接受）

### `Keep_Direction` 实现要点（按"跟随云台"）

需要的量 = **云台相对车头的夹角 Δyaw**：
- **推荐**：`Δyaw = ctrl.GetDelta(imu_pantile.GetAngleYaw() - imu_chassis.GetAngleYaw())`
  ⇒ **正好用上闲置的 `imu_chassis`**；差值抵消，**无需标定零位**，也不受大 yaw 锁死位置影响
- 备选：小 yaw 编码器 `angle[now]`，但需要标 `yaw_zero`（小 yaw 中位对应车头正前方）

摇杆向量从**云台系**旋到**车体系**：
```cpp
speedx = fwd * cosf(rad) - left * sinf(rad);
speedy = fwd * sinf(rad) + left * cosf(rad);
```
⚠️ 符号必须实测（`CHASSIS::Update` 的逆解约定：`speedx` = 前后、`speedy` = 左右）

### 两个编译/设计坑

1. `CHASSIS` / `PANTILE` 是 `CONTROL` 的**嵌套 struct** ⇒ 调用外层类的**非静态成员函数**必须写 `ctrl.GetDelta(...)`，直接写 `GetDelta(...)` 编译不过
2. `Keep_Direction()` **无参数**却要读 `rc.ch[]`，而 `control.cpp` **没有 `#include "RC.h"`** ⇒ 要么补 include，要么改签名 `Keep_Direction(int32_t ch_fwd, int32_t ch_left)`（推荐，与 `Control_Pantile(ch1,ch2,ch3)` 风格一致，且不引入跨模块依赖）

### 赛制现实判断

全自动 + 全向轮（可只平移不转向）+ 大 yaw 锁死 + 走到固定点停下打 ⇒ **两个函数价值都有限**。
FOLLOW 若确认用不上，**直接删 case + 调用**来消除 bug 也是合理选项，不必为了"补齐"而硬写。

**用户决定**：`Keep_Direction` 按"跟随云台"实现（练手，顺便让 `imu_chassis` 有消费者）；**裁判系统用不到，不写**。调用已写成 `ctrl.chassis.Keep_Direction(rc.ch[1], rc.ch[0]);` ✓

### 协议扩展：**帧尾追加，不动现有偏移**

| 项 | 改前 | 改后 |
|---|---|---|
| 帧长 | 32 | **40** |
| `[0..29]` 偏移 | — | **完全不变** ✓ |
| `[30..33]` | CRC 低/高字节 | **`vx` (float)** |
| `[34..37]` | — | **`vy` (float)** |

`RC.cpp` 的 `OnPC()` 里第 70 行与第 77 行各有一句 `const float DB = 0.3f * PI / 180.f;`，同一函数作用域 ⇒ `error: redefinition of 'DB'`。删掉 77 行那句。

**2. `K_NAV = NAV_MAX / 660.f` = 6.06 —— 物理意义错误**
`660` 是**摇杆量程**，不是速度单位；而 `xuc.speed_x` 的单位是 **m/s**。6.06 rpm/(m/s) 意味着视觉要车走 1 m/s 只给 6 rpm 轮速 ⇒ **车几乎不动**。
量级估算（轮半径 R 米）：走 1 m/s 需 `n = 1 / (2πR/60)` rpm；R=0.06m 时 ≈159 rpm，45° 分解再叠系数 ⇒ **K_NAV 合理量级 150~500**，比 6.06 大 30~80 倍。
**标定法**：临时绕开 K_NAV 写死 `chassis.speedx = 1000`，跑 1 秒量实际位移 v，`K_NAV = 1000 / v`。

**3. 失联时没清 `xuc.prespeedx / prespeedy` ⇒ 恢复瞬间暴冲**
失联只清了 `chassis.speedx`，但 `prespeedx` 保留失联前值（如 3000）。恢复后第一帧 `dvx = 目标 - 3000`，被 clamp 到 -200，`prespeedx = 2800` 并**直接下发** ⇒ 底盘突然以 2800rpm 冲出去，再花 ~70ms 降回来。
修：失联分支里补 `xuc.prespeedx = 0; xuc.prespeedy = 0;`

**4. `prespeedx` 自身无限幅 ⇒ 目标超量程时会"积压"**
现写法是「增量限幅 → 累加 → 只在输出端限幅」，`prespeedx` 内部可无限增长。若视觉给了超量程值，`prespeedx` 涨到几万后，即使目标降回 0，也要按 ±200/周期 慢慢降 ⇒ **底盘保持满速 1 秒以上**。
**正确顺序：先限目标，再限增量**：
```cpp
const float tgt_x = std::max(std::min(xuc.speed_x * K_NAV, NAV_MAX), -NAV_MAX);
float dvx = tgt_x - xuc.prespeedx;
dvx = std::max(std::min(dvx, DV_MAX), -DV_MAX);
xuc.prespeedx += dvx;
ctrl.chassis.speedx = xuc.prespeedx;   // 天然不越界，无需再 clamp
```

## 通信协议定稿（2026-10-09，已产出 `docs_上下行通信协议.md`）

### 下行帧（上位机 → 电控）：**40 字节**
`0`header **0xA5** ｜ `1-4`pitch(度) ｜ `5-8`yaw(度) ｜ `9-12`yaw_diff(度) ｜ `13-16`pitch_diff(度) ｜ `17-20`distance ｜ `21`fireadvice(bit0) ｜ `22-24`保留 ｜ `25-28`v_y ｜ `29`保留 ｜ **`30-33`speed_x(float, m/s, 车体系)** ｜ **`34-37`speed_y(float, m/s, 车体系)** ｜ `38-39`CRC16

### 上行帧（电控 → 上位机）：**28 字节**
`0`header **0x5A** ｜ `1`flags(detect_color:1 / reset_tracker:1 / reserved:6 三合一字节) ｜ `2-5`roll ｜ `6-9`pitch ｜ `10-13`yaw ｜ `14-17`aim_x ｜ `18-21`aim_y ｜ `22-25`aim_z ｜ `26-27`CRC16

### ⚠️ 关键口径（易错）
- **上下行角度单位不对称**：**下行 = 度**（视觉定义），**上行 = 弧度**（`imu.cpp` 的 CH010 分支走 `R4(rxData+offset+48/52/56)` 直接读 float，即 HiPNUC `0x91` 欧拉角包原生输出；**建议实测 hex 复核**）
- **速度单位不对称**：下行 m/s ↔ 电控内部 rpm，中间乘 `para.K_NAV`
- **CRC**：CRC-16/MCRF4XX，init `0xFFFF`，反射表，**低字节在前**，覆盖 `帧长-2`（下行 [0..37]，上行 [0..25]）
- **发送 ≠ 接收**：帧长 40 vs 28、帧头 0xA5 vs 0x5A，两套完全独立
- 波特率 **921600**，队列深度 1 覆盖写 ⇒ **下发率上限 200 帧/s**
- 失联 250ms（`TIMEOUT_TICKS` 50 × 5ms）⇒ 停底盘 + 停摩擦轮 + 停火

### 🔴 帧长 32→40 的兼容性后果（必须告知视觉）
电控用 `VerifyCRC16CheckSum(m_frame, 40)` 校验 [0..37]。视觉若仍发 32 字节，则 [30..37] 是**上一帧残留字节**（DMA 缓冲不清零）⇒ **CRC 100% 失败 ⇒ 全部帧被丢 ⇒ 彻底断链**。联调第一步：双方各打 40 字节 hex 逐字节比对。
